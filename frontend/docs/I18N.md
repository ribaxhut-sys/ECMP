# Internationalization (i18n)

ECMP UI supports **Bahasa Indonesia (`id`)** as the default language and **English (`en`)** as a secondary language. The stack is designed for unlimited future locales.

## Stack

| Piece | Location |
|---|---|
| Library | [`next-intl`](https://next-intl.dev/) (App Router, no URL locale prefix) |
| Locale config | `src/i18n/config.ts` |
| Server request config | `src/i18n/request.ts` |
| Date / number / currency | `src/i18n/formatting.ts` |
| Client provider | `src/shared/i18n/LocaleProvider.tsx` |
| Language switcher | `src/shared/i18n/LanguageSwitcher.tsx` |
| Messages | `messages/id.json`, `messages/en.json` |
| Next plugin | `next.config.ts` → `createNextIntlPlugin("./src/i18n/request.ts")` |

## Locale resolution priority

1. **User preference** — `users.preferred_language` (authenticated) / cookie `NEXT_LOCALE` / `localStorage` key `ecmp.locale`
2. **Default** — `id` (Bahasa Indonesia)

ECMP is Indonesian-first. Browser `Accept-Language` does **not** auto-switch the UI to English; English is selected via the language switcher.

Switching language updates messages immediately (client-side), sets the cookie + localStorage, refreshes server components, and (when logged in) calls `PATCH /api/v1/users/me/preferred-language`.

## How to add a translation key

1. Add the key under the right namespace in **both** `messages/id.json` and `messages/en.json`.
2. Keep key paths identical across locales (parity is required).
3. Use ICU-style placeholders where needed: `"passwordMinLength": "Password must be at least {min} characters."`
4. In a client component:

```tsx
"use client";
import { useTranslations } from "next-intl";

export function Example() {
  const t = useTranslations("common");
  return <button type="button">{t("save")}</button>;
}
```

5. Prefer existing keys (`common.save`, `common.cancel`, `nav.*`) over inventing duplicates.

## How to add a new language

1. Add the locale code to `LOCALES` in `src/i18n/config.ts` (e.g. `"ms"`).
2. Add `LOCALE_META` entry: label, short code (`ID`/`EN`), `flagSrc` under `public/flags/`, BCP-47 tag, date format, currency display.
3. Copy `messages/id.json` → `messages/<code>.json` and translate all values.
4. Extend backend allowed languages (`Literal["id","en",…]` / validation set) and OpenAPI `preferredLanguage` enum.
5. No route restructuring is required (locale is cookie-based, not path-based).

## Formatting conventions

| Concern | Indonesia (`id`) | English (`en`) | Helper |
|---|---|---|---|
| Date | `dd/MM/yyyy` | `MM/dd/yyyy` | `formatDate(value, locale)` |
| Date-time | locale short | locale short | `formatDateTime(value, locale)` |
| Number | `1.000,50` | `1,000.50` | `formatNumber(value, locale)` |
| Currency | `Rp` (narrowSymbol) | `IDR` (code) | `formatCurrency(value, locale)` |

```tsx
import { useLocale } from "next-intl";
import { formatDate, formatNumber, formatCurrency } from "@/i18n/formatting";

const locale = useLocale();
formatDate(row.createdAt, locale);
formatNumber(1000.5, locale);
formatCurrency(150000, locale);
```

## Translation conventions

- **Never hardcode UI copy** in JSX/TSX (labels, buttons, titles, empty states, validation, toasts).
- Namespace keys with module prefixes: `complaints.create`, not flat `createComplaintButton`.
- Reuse `common.*` for shared actions.
- Enum display labels live under `status.*`, `priority.*`, etc. — not inline maps of English strings.
- Form validators should accept a translate function (`t`) and return localized messages, or return message keys.
- Backend API remains language-neutral for domain payloads. Localize only user-facing messages/emails via `app/core/i18n_messages.py`.

## Language switcher placement

- Header (compact)
- Login / forgot-password / reset-password (compact)
- Profile → Language card (full)
- Settings → Language card (full)

## Backend

| Item | Detail |
|---|---|
| Column | `users.preferred_language` (`VARCHAR(8)`, default `id`) |
| Migration | `0038_preferred_language` |
| Me field | `AuthMe.preferredLanguage` |
| Update | `PATCH /api/v1/users/me/preferred-language` |
| Email | Password-reset (and future change-password) templates pick language from user preference → `Accept-Language` → `id` |

## Manual test checklist

1. Cold start with cleared cookies → UI is **Indonesian**.
2. Switch to English in header → UI updates without full navigation to a locale URL.
3. Refresh → English persists (cookie).
4. Log in → preference saved via API; `/api/v1/auth/me` returns `preferredLanguage`.
5. Log out on another browser with `Accept-Language: en` and no cookie → English until user overrides.
6. Walk every route (login, dashboard, complaints CRUD, queue, assignments, resolutions, attachments, reports, users, settings, profile/security) in **id** and **en**.
7. Trigger validation errors on create-user / create-complaint / change-password — messages match locale.
8. Forgot-password email log line shows localized subject for the user’s language.
9. Confirm no missing-key warnings in the browser console (`MISSING_MESSAGE`).

## Verifying key parity

```bash
node --input-type=module -e "import en from './messages/en.json' with { type: 'json' }; import id from './messages/id.json' with { type: 'json' }; function keys(o,p=''){let r=[];for(const[k,v] of Object.entries(o)){const n=p?p+'.'+k:k; if(v&&typeof v==='object') r=r.concat(keys(v,n)); else r.push(n);} return r;} const ek=new Set(keys(en)); const ik=new Set(keys(id)); console.log([...ek].filter(k=>!ik.has(k)), [...ik].filter(k=>!ek.has(k)));"
```

Both arrays should be empty.
